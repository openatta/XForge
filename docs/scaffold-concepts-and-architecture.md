# XForge 脚手架规则文件：概念与架构

> 共同概念、对象与不变量在 [概念与架构](concepts-and-architecture.md)。
> 这份只讲**规则文件这一层**：脚手架里应该有哪几族规则文件、每一族归谁写归谁读、
> 控制面从每一份里读什么。不含字段表、不含 schema、不含迁移方案。
>
> 主文档持有的东西这里不复述，只引用名字。

---

## 0. 这一层的判据

主文档《五个提问者》给了分类的唯一依据：**谁、在哪一刻、为了决定什么而读它。**
它推出的操作原则（主文档《文件是权威，回复是视图》与《能让控制面操作的就别开文件》）在这一层落成一个具体后果：

> **文件保持完整，回复按需裁剪。**

这一层的每一次「要不要拆」都按这条判 —— 包括 §2.2 那个最容易被翻案的决定。

---

## 1. 两个核心

脚手架只有两件事必须做对，其余全是支撑：**流程**与**治理**。

- **流程** —— 一个 Change 要走什么路：哪些站、每站产出什么、每站凭什么才能离开、卡住了往哪退。
- **治理** —— 两条基线（主文档《两条基线》）。它的机制、开关组合与保证层都在主文档；
  这一层只管**它们以什么形态住在盘上**。

---

## 2. 四族规则文件

按「谁有权改它、多久改一次」切，得到四族。这个切法不是新发明的 ——
现有的所有权分区表已经在按同一条线执法，把它明确成概念只是给它一个名字。

**归族按文件的主体归属定。** 一个受管文件里可以有一块由标记划出、归项目所有的区域
（Skill 那一层的本地化区），那是**显式例外**，不改变它属于哪一族 ——
但升级事务必须认识那个标记（§2.2）。

### 2.1 宪法级 —— 这个项目自己的决定

**章程**：长期工程原则。唯一一份会被逐条机读对照的散文。
**清单**：这个项目启用了什么、治理哪几条基线、跑哪条默认流程、用什么命令验证自己。

- **谁写**：人。控制面只动少数几个锚点字段（版本、验证声明），且必须留下审计。
- **谁读**：章程 —— 门读它的标题清单，Agent 读它的正文；清单 —— 所有提问者，
  其中**执法路径每一次工具调用都要碰它**。
- **变化频率**：很少。升级不动它们，只推进版本锚点。

**章程的标题是 id，正文才是内容。**
逐条对照是按标题匹配的，所以改一个标题等于改一个 id ——
它会让此前每一份引用过该条的台账对不上。**改标题是一次治理变更，不是一次措辞修改。**
改正文不是。这条区别必须写在章程文件自己的开头，因为它是唯一会被误当成排版调整的破坏性操作。

**清单必须小。** 它在执法热路径上 —— 执法靠它找到本项目的策略集，然后只读策略集。
凡是「只有某个 Stage 才需要」的东西都不该进清单：清单回答的是「这个项目是什么样」，
不是「这一站要干什么」。

### 2.2 机制级 —— 随脚手架分发，由项目选用

**流程定义**，以及它所调度的一切：门、规则、权限策略、执法钩子、审批策略、
子 Agent 定义、Skill、脚本、外部审批服务声明。

- **谁写**：脚手架分发，项目选用。**Agent 写入被拒。** 唯一的例外是本地化区（主文档《本地化区》）：
  那一块由人写，落在宪法级那条线上，只是住在机制级的文件里。
- **谁读**：控制面判定与执法；Skill 的正文由 Agent 读。
- **变化频率**：随版本升级。**这一族就是升级事务的全部作用域** ——
  快照它、分类它、合并它、回滚它；其余三族升级一个字都不动。

**这一族的共性：它们是机制，不是内容**（主文档《受理》：门的逻辑随脚手架分发，门的输入来自项目）。
带本地化区的文件在升级时做移植，标记可定位是这条成立的全部前提。

#### 流程文件不拆

一个流程文件里装着两种读者的东西：**判定图**（站、门、出口条件、审批策略）给控制面，
**写作材料**（每份产出的指令、大纲、标记）给 Agent。后者通常占大头。

**不拆。** 理由是 §0 的判据：

- 一个流程是**一个决定**。「这一站产出 X」和「X 必须包含什么」是同一句话的两半。
  拆开就制造了一对必须互相吻合、却没有东西检查它们是否吻合的文件。
- 升级事务逐文件分类。一个流程变两个文件，合并面翻倍，并且会出现「半个流程升级了」的状态。
- 权威唯一。两半不一致时，没有任何东西能说哪半对。

**代价由回复侧承担，不由文件侧承担**：判定图常驻，写作材料在进入那一站时按需转发。
文件多大无关紧要，因为没有人需要整份读它 —— 前提是主文档的 `名字不单飞` 与 `切片自称完整` 成立。

#### 每份产出要标注它欠不欠的两个条件

主文档《欠不欠的两个条件轴》定了语义（两个条件轴，不满足时是「不欠」而不是「待写」）。
这一层的事是**它们写在流程文件的哪里**：

| 轴 | 声明成什么 | 不写会怎样 |
| --- | --- | --- |
| **治理依赖** | 这份产出依赖哪条基线的开关 | 关掉基线的项目被要求写一份没有对照物的文件 |
| **侧** | 规格侧 / 实现侧 | 撞车 —— 接口 delta 属规格侧（全 Change 一份），但产出它的站属实现侧（按方案跑）；不标注，方案 `test` 的设计站就会去写一份它没有理由碰、而且已经被另一个方案写好的共享文件 |

第一个轴今天已经有形状（`requiredWhen`），第二个还没有。两个要写在同一处、用同一套词，
因为它们回答的是同一个问题。

### 2.3 事实级 —— 已经被认可的东西

**两条基线**：规格、接口。各带**一份索引**。

- **谁写**：**只有归档合并**（`基线只由归档推进`）。没有命令能写它，手写被策略拒绝。
  这是整个系统里权限最窄的一族，因为它是「什么算数」的最终答案。
- **谁读**：控制面合并与枚举；Agent 在写 delta 之前。
- **变化频率**：每次归档。

**delta 与基线是同一份内容的两个生命阶段，不是两种文件。**
在 Change 里叫 delta（提案），归档后叫基线（已认可）。中间那一次合并是唯一的转换，
也是唯一该产出索引的时刻。

#### 索引，分两层

每条基线一份索引，回答且只回答一个问题：**这个项目记录过哪些条目、它们在哪。**

它必须分两层，因为它是唯一一个会**无界增长**的常驻项（`第0级有界`）：

| 层 | 内容 | 加载 |
| --- | --- | --- |
| **域层** | 这个项目记录了哪些能力 / 哪些契约域 —— 数量是几十 | **常驻** |
| **条目层** | 某个域下面有哪些条目 id、各在哪个文件 | **按域取** |

分层不损失它的用途：**「先复用已有的名字再发明新的」本来就是先选一个域，再看它下面有什么。**

其余三条性质：

- **由归档合并产出**，不是扫描缓存（`重算的不能作判据`）。合并本来就在同一个事务里写基线文件，
  顺手多写一份索引是免费的；而扫描重建出来的东西是缓存。
- **提交。** 不提交则新克隆和 CI 上必须回退到全量扫描，于是同一个问题有两种答法、两份代码、
  两种性能特征。
- **与实现方案无关**：基线由归档推进，而归档是 Change 级的（`归档唯一例外`）。

**索引不是优化，它是让一条指令第一次变得可执行。**
流程指令里写着「先复用这个项目已有的名字」和「读元素 id，绝不要凭记忆重打」——
而查法是把全部文档 glob 出来逐个解析。**一条要求你先查的指令，配上一次全量扫描的查法，
就是一条会被跳过的指令。**

它的限度在主文档《影响面自述》：**「本站触碰的是哪个域」是从一份无人核对的自述推出来的。**

### 2.4 记录级 —— 一次改动的全部

一个 Change 目录里的一切，归档后整体冻结（`归档后不再变`）。

#### 谁写：三层，权限互斥

| 层 | 内容 | 谁写 | 手写 |
| --- | --- | --- | --- |
| **声明** | 跑哪条流程、风险与影响面；作用域（按方案）；意图文档；工作包计划 | Agent / 人 | 是 |
| **断言** | 五类台账（主文档《台账》） | Agent 或人 | **必须** |
| **证据** | 门的运行记录、各类 receipt、审计索引 | **只有控制面** | **禁止** |

**断言层与证据层必须分开住。** 两者的写权限恰好相反，读者却是同一个 —— 所以分开不是为了少读，
**是为了让「我能不能手写这个文件」这个问题从文件位置上就能回答。**

#### 目录：规格侧一份，实现侧按方案

分界与它的理由在主文档《实现方案》。这一层只给布局：

```text
changes/<change-id>/
  ── 规格侧 · 一份，所有方案共享 ──
  流程与分类声明
  提案
  规格 delta
  接口 delta

  ── 实现侧 · 默认方案（不带 id），直接在本目录 ──
  作用域 / 设计 / 工作包 / 台账 / 证据 / 审批 / 阶段状态

  ── 实现侧 · 具名方案 ──
  <方案 id>/
    作用域 / 设计 / 工作包 / 台账 / 证据 / 审批 / 阶段状态
```

> **不给方案 id → 落在 Change 目录本身；给了 id → 落在该 id 的子目录下。**

**默认方案不占用一个名字**，所以单方案项目的目录布局与没有这个特性时**一模一样**。

## 3. 控制面的读取边界

### 3.1 散文与条目

一份文档里通常同时有两种东西，而控制面只碰其中一种（`不读散文的意思`）：

- **骨架**：文件在不在、声明的章节标题有没有、标记出现够不够次数。这是结构性存在检查，不是理解。
- **条目**：有 id、有字段、能被比对和合并的东西 —— 规格里的 Requirement、接口里的元素、
  台账里的每一条。

**标记是把两者分开的那把刀。** 它让一段散文里的**条目区域**变得机器可定位，
于是一条规则可以被**计算**，而不是被概括。没有标记，控制面要么读不懂，要么只能去猜。

这条边界有一个必须一起接受的推论：**它限制了流程能声明什么样的出口条件。**
一个只能靠读懂一段话才能判断的条件，不是一个可以写进流程的条件 ——
它要么被改造成条目，要么就交给人（变成主文档《人的介入点》的一次审批）。

### 3.2 三档读取契约

每一份文件都必须说清：**控制面从它那里读什么。** 只有三档：

| 档 | 控制面读什么 | 内容归谁 |
| --- | --- | --- |
| **条目级** | 逐条读标识、结论、引用、署名，用于判定与合并 | 写的人，但**形状由契约定死** |
| **骨架级** | 只读「文件在不在、声明的标题有没有、标记够不够次数」 | 写的人全权 |
| **混装** | 标记划出的条目区按条目级读；其余按骨架级 | 两段各按各的规矩 |

**四族按档分类：**

| 族 | 文件 | 档 |
| --- | --- | --- |
| 宪法级 | 清单 | 条目级 |
| 宪法级 | **章程** | **混装** —— 标题是条目，正文是散文 |
| 机制级 | 流程、门、规则、策略、钩子、审批策略、Agent、脚本、MCP | 条目级 |
| 机制级 | Skill | 骨架级（正文归 Agent） |
| 事实级 | 两条基线及其索引 | 条目级 |
| 记录级 | 见下表 | —— |

**记录级逐份：**

| 产物 | 档 | 控制面具体读什么 |
| --- | --- | --- |
| 流程与分类声明 | 条目级 | 跑哪条流程、风险、影响面 —— 全部进判定 |
| 作用域声明 | 条目级 | 这个方案可以动哪些路径 —— 「树里有改动但没人认领」这个检测的判据，也是进站时投影站级策略的源 |
| 工作包计划 | 条目级 | 包 id、依赖、写入路径、验证命令、完成判据 |
| 规格 delta | 条目级 | Requirement id（归档合并 + 核对引用） |
| 接口 delta | 条目级 | 元素 id、所属模块、是否破坏性、摘要 |
| 五类台账 | 条目级 | 主文档《台账只有一个形状》的统一形状 |
| 提案 | 骨架级 | 标题清单 |
| 设计 | 混装 | 骨架 + 被否决的替代方案（条目） |
| 保证说明 | 混装 | 骨架 + 覆盖表（条目） |
| 门运行记录 / 各类 receipt | 条目级 | 控制面自己写、自己读，形状由「要证明什么」决定 |

**没有「控制面完全不读」这一档。** 连散文也要验骨架 ——
骨架是唯一能在不读懂内容的前提下，说出「这份东西写完了」的手段。

**章程落在混装档**，这不是巧合：它和 §2.1「标题是 id，正文才是内容」是同一句话的两种说法。
两处独立推导得出同一个结论，是这套分类自洽的一个旁证。

**Skill 落在骨架级有一个后果**：控制面无法判「这份 Skill 覆盖了本站要求」——
骨架对所有站都一样。命令行那一层把这条降级成了存在性检查，并记为开放问题。

**影响面在声明与流程两边都是列表**（主文档《影响面自述》）：流程读它的写法是「任一命中即成立」，
声明也写成列表，中间少一次翻译。「没有任何东西核对它」这句必须写在声明旁边。

### 3.3 一份散文凭什么存在

每一个评审型的 Stage 都会同时产出一份散文和一份台账，讲的是同一件事。
判据是 `散文要有不可约判断`：

> **一份散文必须持有一个台账装不下的判断。没有，它就不该存在。**

没有这条规则，写作指令就得用一大段划分「什么别写在这里」，而重复照样发生 ——
**指令在对抗重复，说明对抗输了；赢的办法是让重复无处可写。** 按这条规则判：

| 产物 | 台账装不下的那个判断 | 去留 |
| --- | --- | --- |
| **提案** | 为什么做、边界在哪、非目标是什么、为什么选这条流程 | **留** |
| **设计** | 技术路径、集成点、失败模式、迁移与回滚 | **留**（混装） |
| **保证说明** | **连贯性** —— 提案、规格、设计、测试、实现是不是在描述同一个行为，哪里分了叉 | **留**（混装） |
| **澄清** | 无。它的章节逐一对应出口条件台账的字段 | **去** |
| **检查报告** | 无。它唯一独有的事实是「这次评审覆盖了哪几个维度」，而那是一张表 | **去** |

两处删除的去向：

- **澄清** → 材料问题那份出口条件台账本来就承载全部内容，产出它的那一站从此只产出台账。
- **检查报告** → 「覆盖了哪几个维度」进评审发现台账的**整体结论**（统一形状里预留的那一层）。

**一个 Stage 只产出台账，是完全正常的。** 台账本来就是它要交的东西；
散文是附加物，不是每一站都欠。

活下来的三份里**有两份是混装的** —— 所以「显式标出条目区」不是边角需求，是多数情况。
一份混装文档必须让作者看得出哪一段改了会让机器失灵：实测过一次，
作者给一个标题加了限定语，内容全对，标记不再解析。

## 4. 能让控制面操作的，就不要让 Agent 开文件

原则在主文档《能让控制面操作的就别开文件》。这一层给对照表：

| 要做的事 | 怎么做 |
| --- | --- |
| 读流程的任何一部分 | **命令**（不开流程文件） |
| 读这个项目有哪些能力 / 契约域 | **命令**（索引域层，常驻） |
| 读某个域下有哪些条目 | **命令**（索引条目层，按域取） |
| 读某个条目的正文 | **命令**（按 id 取） |
| 读章程有哪几条 | **命令**（标题清单） |
| 起草一份台账的骨架 | **命令**（返回内容，断言字段留空，由作者落盘） |
| 写基线 | 只有归档合并 —— 没有命令，也不许手写 |
| 写证据 | 只有控制面 |
| 写断言 | 只有 Agent 或人 —— 控制面只能起草骨架 |

不属于任何一族的是**派生物**：锁文件、投影记录、审计链、升级事务的工作目录。
它们不是规则文件，是输出。判据是 `重算的不能作判据`。

**有两种派生物进判定**：基线索引，与投影出的作用域策略（进站时按方案，派工时按包）。
为什么它们算数而别的派生物不算，判据在主文档《写入范围的权威》。

这一层要说的是**它们不属于任何一族**。作用域策略尤其容易被误放进机制级 ——
它确实是一份策略，执法确实读它 —— 但机制级的定义是随脚手架分发、且等于升级事务的作用域，
而它两样都不占：它随 Change 生成、随 Change 冻结。

**四族分类的那条价值因此不受影响**：从文件位置能回答「我能不能手写它」，
而派生物的答案一律是「不能，它是输出」。**需要特判的例外只有一个**：本地化区。

## 5. 本层的非目标

**不拆流程文件。** 代价：文件会大。不是问题 —— 成本在回复侧，已由加载三级解决。

**不保留没有不可约判断的散文。** 澄清与检查报告不作为产出存在。
代价：给「后来的人」的那份叙述没有了 —— 但那个读者本来读的就是台账加门证据。

**规格条目不带摘要。** 接口元素带摘要，所以「把一个枚举放宽」这种修改是可判定的；
规格侧不做同样的事。代价明确：**一条 Requirement 措辞改了而 id 没变，没有任何东西会说。**

**索引提交。** 不提交更「干净」，但会让同一个问题有两种答法、两份代码。取简。

## 6. 本层已定的一件事

实现方案这个轴留给这一层的问题（方案能不能跑不同流程、归档要哪些方案到终点、站级范围由什么声明）
都已在主文档《实现方案》与《写入范围的权威》定死。这一层自己定的只有一件：

> **作用域按方案，不在流程与分类声明里。**
>
> 「树里有改动，但没有任何工作包声明它」这个检测若是 Change 级的，两个方案写的是不同的树，
> **一个方案的全部产出在另一个方案看来都是「无归属路径」**，双方会被自己的伙伴卡死。
> 作用域讲的是实现路径，按主文档《实现方案》那条分界它属实现侧；放在实现侧，检测自然降到方案级。
>
> **它和派工投影出的作用域策略是同一件事的两端**：投影回答「这个包能写哪里」，
> 作用域回答「树里没人认领的改动算谁的」。两端都在方案级，中间不需要翻译。
> 代价：每个方案多一份作用域；单方案项目按默认方案落在 Change 目录本身。
