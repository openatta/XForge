## 3. 对照组说明了什么

同一天、同一条链路，只有代码不同：

| | 文档基线 09-17 | **今天 `58e6dec`（1.0.1）** | 今天 `854dceb` | 今天 `ad2d787` |
| --- | ---: | ---: | ---: | ---: |
| 外层轮 | 4 | **2** | 2 | 2 |
| output | 17 640 | **22 093** | 17 480 | 18 992 |
| xforge 调用 | 32 | **35** | 36 | 37 |
| 工具调用 | 39 | **60** | 52 | 53 |
| output/分 | 3556 | **2594** | 2147 | 2172 |

**1.0.1 的代码今天也是 35 次调用、60 次工具、2594 output/分**，与今天我们的代码同档，而与 09-17 的 32 / 39 / 3556 明显不同。所以：

- **工具调用从 39 涨到 50–60，不是这轮改动引入的**；1.0.1 今天比我们还高。
- **吞吐腰斩（3500 → 2100–2600 output/分）也不是**；模型字符串与 09-17 完全相同，所以不是换了模型，是服务端与链路的当日状态。
- 在这一对里，`ad2d787` 的 output 比 1.0.1 **低 14%**。

两处让 09-17 与今天不可直接比的原因，都与这轮改动无关：

1. **oracle 条件**：文档那批用 3/4/4，1.0.1 起已是 5/7/7。文档的数字比它自己的仓库状态旧。
2. **当日链路状态**：同样的 1.0.1 代码，09-17 是 32 次 / 3556，今天是 35 次 / 2594。

> **教训**：跨天比 live 数字要先有同日对照组。单看「今天 vs 某天的文档」永远分不清代码与环境。

## 4. `XF-ASSEMBLE-014` 的假阳性（`854dceb` → `ad2d787` 修掉）

`854dceb` 的三场都报「钩子装上了但跑不起来」，而那三棵树上钩子一直在跑。
原因：那条检查拿**自己进程的 PATH** 去替**宿主进程**回答。live harness 正是两边不同的形状
（模型会话的 PATH 里有 shim 目录，harness 调 `doctor` 的那一份没有）。

`ad2d787` 之后 `enforcement` 只看钩子在不在宿主原生位置里（验得出来的那一半），`014` 降为 `warning`
且不参与判定。此后三场（A 一场 + B 两场）的装配体检都是：

```json
{"codes": [], "exit": 0, "wrote": [], "repair": {"changed": 2, "leftCodes": [], "exit": 0}}
```

`LT-09`（真树上装配干净）、`LT-10`（`doctor` 不写盘）、`LT-11`（注入漂移被 `repair` 收敛）**首次在真机验证通过**。

## 5. B 的那次 deny 是执法在正确工作

执行者把交付台账写到了 `<project>/ledgers/deliveries/P-01.yaml`（项目根），
而不是 `xforge/changes/<id>/ledgers/deliveries/P-01.yaml`。那个位置不在包投影的 `allow`
（`invoicely/core.py`、`tests/test_core.py`）里，钩子报 `XF-ENFORCE-002` 拦下；模型随后改对，
台账最终落在正确位置。`deepseek-v4-flash` 在路径上比 Claude 弱，0.8.6 同引擎也出现过 3 次。

> **已知 harness 计数 bug（未修）**：`observe()` 对 `tool_use` 去了重，`tool_result` 那一支没有。
> 同一次 deny 同时出现在主会话与子 Agent 转录里会被记成 2。上表那一格写的是实际值 1，
> `summary.json` 里是 2。`tool_uses` 不受影响。

## 6. solid-rework 停滞的原因（产品缺口，非回归）

模型把植入的设计矛盾（R-0003）**修对了**，然后发现了一条真实的规格歧义：
`REQ-billing-payments-003` 的三条 WHEN 不互斥 —— 总额为 0 的新发票同时命中
「没有任何收款 → `open`」与「余额为 0 → `paid`」，条文没给优先级。
执行者按站的停下条件停在 `blocked spec-conflict`。

模型自己说得很准：

> 控制面没有为这个 token 登记 remedy，所以没有现成的解法可念给你。

于是 `state` 的 `blockers` 是**空的** —— 从治理角度确实没有东西挡着。模型连着三轮转向人求裁决，
而 harness 的模拟人只会做脚本化的动作（`attest` / `approve` / `rework`），答不了规格问题，
撞上「位置与阻塞连续三轮不变」的停滞规则。

三方都没做错，缺口是真的：**执行者能停在一个控制面看不见的理由上**，`state` 就给不出可执行的下一步，
自动驱动必然死锁。待排。
