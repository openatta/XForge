# XForge 原则

> 这一页是判断依据，不是介绍。遇到「该不该加这个功能」「这样实现对不对」，回到这里。
> 具体机制见 [治理模型](governance-model.md)，整体结构见 [概念与架构](concepts-and-architecture.md)。

---

## 0. 本质

**XForge 是一台把「无法核验的主张」转换成「绑定版本、可归因的事实」的机器，
好让互不连续、互不信任的参与者之间可以交接工作，而不必相信上一个人的说法。**

一次交付里，大量东西只能靠相信才能往下传——「我审过了」「测试通过了」
「这个破坏性变更有人批准了」。传统上这靠人的信誉。引入 Agent 之后这条链断了：
Agent 写的散文和真话在文本上无法区分，而且它随时可以写出任何一句。

XForge 的回答不是「让 Agent 更可信」，而是**取消对可信的需求**。

---

## 1. 四个动词，不可互换

> 一条 Rule 可以**指导**，一条 PermissionPolicy 可以**守卫**，
> 一道 Gate 可以**证明**，一次 Approval 可以**授权**——
> 从不让其中一个顶替另一个。

四种强度，四种代价，四种失效方式。把弱的当强的用，就是在没有证据的地方声称有证据。

操作化表述：**只有 CLI 的 JSON 输出与 Gate Evidence 算事实。**
Agent 的自然语言结论、聊天记忆、勾选框、自报退出码，一律不是事实。

---

## 2. 四层，地基在下

| 层 | 是什么 | 载体 |
| --- | --- | --- |
| ④ **授权** | 人的决定，机器不可替代 | Approval 收据、`approvedBy`、`decidedBy` |
| ③ **记录治理** | 让约定活过单个 Change | Spec 合并、Contract 合并 |
| ② **流程** | 什么时候允许往前，退到哪 | Stage graph、exit 条件、rework 路线 |
| ① **证据链** | 唯一的事实来源 | Gate Evidence、转移收据、审计链 |

前三层存在的意义，是让第四层**落在正确的时刻、并且事后可归因**。

---

## 3. 事实必须绑定状态

一个事实必须是关于**某个确定状态**的，否则不可传递。

Gate Evidence 绑 `contentRevision`，审批绑 `governingRevision`，转移收据成链。
**改一个字，之前的证明全部失效**——这不是副作用，这是定义。

推论：**必须在最后一次写入之后、一次性运行 Gate。**
先跑一个 Gate、再改 Artifact、再跑下一个，会让先跑的那个变陈旧。

---

## 4. 授权不可被机器生成

机器可以证明「命令跑过了」，永远不能证明「这个背离是可以接受的」。

**任何要求具名的字段，CLI 都不得代填。**
Agent 填一个人的名字，就是记录一份没人给过的授权——
而伪造的那一条，此后永远与真的无法区分。

`xforge approve` 的决定词只能来自活的终端提示，不能来自 argv 或工具调用。
这是结构性的，不是提示性的。

---

## 5. 参与者是不连续的

一次完整交付是**若干个人在若干个时刻各自触发一次**，不是一个连续的会话。

**每一段都从零开始，只继承证据，不继承理解。**

这条推出两个结果，缺一不可：

- 冷启动成本高是**设计目标**，不是缺陷。系统刻意不让第 N 段继承第 N−1 段的判断。
- 因此，**任何假设「上一段」存在的机制都是错的**。

---

## 6. 响亮的错误答案好过安静的错误答案

一道声称在检查却什么都没断言的 Gate，比没有这道 Gate 更糟——
它让一条 `must` 级 Rule 失去唯一的强制手段，而没人会发现。

**拒绝是一个未被回答的问题，不是一次失败的检查。**
`builtin: declared` 的 Gate 在项目没有声明命令时**拒绝**，不是放行。

同理：报告要诚实到自己承认弱点。
覆盖档分 `instructed` / `guarded` / `structural` / `verified` / `approved`，
是因为它们强度不同；把弱的报成强的，等于在覆盖报告里撒谎。
反过来也一样：把强的报成弱的同样是撒谎——一条被 PermissionPolicy 守着的 Rule
同时报 `guarded` 与 `uncovered`，是在同一个数组里说 P 和非 P。

**一个预填的默认值是一个安静的答案。** 只有当答错了别处会抓住时，它才是安全的。
`change.yaml` 其余四个布尔键预填 `false` 是对的：risk 错了 Flow 资格会拒，
security 错了有扫描 Gate。而 `moduleContract` 没有别处——它是唯一没有旁证的资格键——
于是预填的 `false` 不是「什么都不声称」，是把整层契约治理关掉的那个答案，
预先写好，递给那个没有下一段能再问一次的问题。现在它是占位符，不答就加载不了。

---

## 7. 加信息不改变行为

**六次实跑证明**：往 Agent 眼前放东西——能力、指令、甚至一个正确且必需的事实——
默认采用率是 **0**。

有效的只有两类：

1. **让错误做法在机制上不可能发生**
2. **删掉或修正一个错的东西**

提「加个 X 让 Agent 少走弯路」之前，先问「有没有一个错的可以删掉，
或者能不能让那条错路根本走不通」。

---

## 8. 一件事只做一遍

同一个概念不该有两份实现、两份清单、两处计算。

已知违反此条的地方（见审计）：Spec 与 Contract 是同一套方案的两个实例、
成熟度分叉；三个 Flow 之间 78% 逐字重复；治理资产路径清单存在四份。

每一处都不是理论问题。路径清单那一份已经漂移过一次；「这条 Rule 是否被强制」
那一份漂移了两次——两处算法各漏了一个字段，各自产出一份自相矛盾的覆盖报告——
现在合成了 `resolveRuleEnforcement` 一个函数。**解法不是把两处改成一致，
是让它们没有第二处可漂。**

---

## 9. 成本用 token 记，不用美元

美元随模型和费率表平移，跨趟不可比。
报开销一律给 **输入·命中 / 输入·未命中 / 输出** 三栏。

已测得的结构（opus-5，一趟完整 solid）：
**输入·命中 92%，输入·未命中 6%，输出 2%。**

推论：**在输出上做的优化测不出来。** 提任何降成本改动前，
先问它动的是 92% 还是 2%。

---

## 10. 行为结论不跨模型

从实跑得出的**行为类**结论（Agent 调了什么、打开了什么、跳过了什么），
在换模型前只是那个模型的结论。成本类结论跨模型也不可比。

改 Skill 或 CLI 入口之前，先在目标模型上量一次。
