## 0. 这一族怎么组织

三条规矩，目的只有一个：同一句话不许在两份文件里各存一份，因为没人检查它们是否还吻合。

- **一条断言只出现一次。** 主文档持有断言，子文档只引用名字，不复述内容。
  可检验形式：任何一句同时出现在主与子里的话都是缺陷，能 grep。
- **改了会牵动 ≥2 份子文档的进主文档，只牵动一份的留在那一份。** 开放问题不上移 ——
  主文档只持有定死的断言；一条未决的跨层要求记在它的实现方那一层，不只记在提出方。
  这条判据只用于决定往上加什么，不用于把主文档里的东西往下搬：搬错的代价是造出一对必须互相吻合的文件。
- **跨文档引用用名字，不用序号。** 不变量与裁剪规则用名字（§10、§8.5 每条都有），
  主文档的一节用它的标题（写「主文档《人的介入点》」）。所以标题也是 id：改标题是结构变更，改正文不是。
  文档内部可以用编号，那不会跨文件失效。术语在文末《术语》。

## 1. 定位

XForge 不写代码，不写文档，不做判断。真正推进工作的是 Agent 按 Skill 写文件。

控制面在四件事上有权力：**告诉 Agent 它在哪**、**把跑过的东西刻下来**、**把人说过的话记下来**、
**在条件满足时让状态机走一格**。除此之外它什么都不做，而且必须显得什么都不做 ——
一个会替你做判断的控制平面，它记录下来的东西就不再能作为证据。

这决定了一件反直觉的事：**让控制面「多做一点」几乎总是错的方向**。
「帮我把台账生成出来」听起来是省事，实际上是让工具替人做出那份台账存在的意义所在的那个断言。

## 2. 五个提问者

规则文件、命令回复、Skill 正文，都不能按「它长什么样」分类，只能按：

> **谁、在哪一刻、为了决定什么而读它。**

| 提问者 | 什么时刻 | 需要的形态 |
| --- | --- | --- |
| **控制面 · 判定** | 每次读状态、每次移动 | 小、条目化、有 id |
| **控制面 · 合并** | 归档 | 稳定 id + 条目化 |
| **控制面 · 执法** | **每一次工具调用** | 极小 |
| **Agent · 写作** | 进入一个 Stage 那一刻 | 可以大，但必须按需送 |
| **后来的人** | 归档之后 | 完整、冻结、自解释 |

一份规则文件如果说不出它服务哪个提问者，它就不该存在。一次命令回复如果说不出它在为哪个提问者
的哪一个决定服务，它就该更短。**这是「够用就好」的可操作形式**，三层共用它。

前三个提问者在同一个进程里，第四个在模型里，第五个在若干年后 —— 同一份文件对它们的形态要求
不可能一致，这是「文件是权威，回复是视图」（§8.1）的来源。

## 3. 谁能写什么

写权限有两个互不相干的轴，它们经常被当成一件事：**能写哪一类文件**（§3.1）与
**能写哪些路径**（§3.4）。前者决定一份东西算不算证据，后者决定一次写入合不合法 ——
一个 Agent 完全可以有权写台账、却无权写这个目录。

### 3.1 两类文件，两种写权限

一个 Change 的目录里住着两类东西，它们长得很像，性质完全相反：

| | **证据** | **断言（台账）** |
| --- | --- | --- |
| 内容 | 跑过什么、结果是什么、绑定到哪个内容修订 | 谁、说了什么、依据是什么 |
| 谁能写 | **只有控制面** | **只有 Agent 或人** |
| 手写 | **禁止** —— 手写的证据不是证据 | **必须** —— 工具代填的断言不是断言 |
| 例子 | 门的运行记录、各类 receipt、审计索引 | §7 的五类台账 |

**两个方向都是硬边界，而且都有反例撑着。** 往一边越界 —— 允许手写证据，那么「门过了」就只是
一句话；往另一边越界 —— 工具替人填断言，那么「有人确认过」也只是一句话。

> 一句话记法：**工具能证明的，人不许说；人才能断言的，工具不许写。**（`写权限二分`）

### 3.2 起草

控制面可以把自己已经知道的事实（执行 id、基线提交、改动路径、内容修订）渲染成一份台账的骨架，
但那个说「这一站验证过了」的字段必须由署名的人填。

> **起草是一种输出形态，不是一个动词。** 共性是三条：**在回复里返回内容、不落盘、断言字段留空。**

它可以挂在任何一个不为此付额外代价的调用上。**挂在哪里是命令行那一层的事；
「返回内容、不落盘、断言留空」这三条是这一层的。** 不落盘的理由：断言字段本来就要作者逐个填，
骨架必须经过作者；而「工具不写台账」这条边界比省一次转写值钱。

### 3.3 署名出现两次

一个需要人负责的结论，在盘上有两处痕迹：**台账条目里的署名字段**（Agent 转录）
与**审计链里的事件**（控制面写，且校验身份）。

两处必须吻合。按 §0.1 的判据，这本来会是一个「没人检查的吻合关系」—— 所以它必须被检查：

> **审计链是权威；门在受理一份台账时，必须核对台账里的署名与审计事件一致。对不上是损坏，不是分歧。**

**执法的只有门。** 「验」也看这一条，但它只报告不阻拦 —— 两个能拦的检查者而没有优先级，
就是下一个「没人检查的吻合关系」。门绿而验红，说明验发现了门没覆盖到的范围，那是一份
待修的缺陷报告，不是一次否决。

这条不能省成「约定作者别抄错」。**署名可引用，不可编造**（`署名可引用不可编造`）：
凡是记录判断的地方，名字都要对照仓库真实记录的身份校验 —— 决策者可以被引用，不能被发明。

### 3.4 写入范围的权威

「这一站能写哪些路径」有四处说法。四份说法没有优先级，就等于没有边界，所以：

> **执法的只有权限策略。** 其余三处各有各的用途，但都不拦人。

| 在哪 | 是什么 | 拦不拦 |
| --- | --- | --- |
| **权限策略**（机制级） | 执法在每次工具调用时读的那一份 | **拦** |
| 方案的作用域声明 | 这个方案可以动哪些路径 | 拦 —— 但拦它的是进站时由它投影出来的那份策略 |
| 工作包计划的写入路径 | 它在 Apply 的细化，一个包一段 | 拦 —— 但拦它的是派工时由它投影出来的那份策略 |
| 站 Skill 的「边界」 | 写给读它的 Agent 看，让它不必靠推理找边界 | **不拦** |

没有独立的「授权级别」字段：站级范围与执行者分型都由作用域的投影承担。

最后一条要说死：**一段散文永远不能扩大或缩小可写范围**（`不读散文的意思`）。

#### 分发的策略怎么读到一个 Change 的计划

权限策略随脚手架分发，一份管所有项目；工作包计划是每个 Change、每个方案一份。
一份分发的策略凭什么知道「这个包只能写这几条路径」：

> **派工时把该包的写入路径投影成一份作用域策略，绑定到那一刻铸出的执行身份。**

选它而不选「策略里放占位、执法时求值」或「执法时注入计划」，理由是执法在每一次工具调用上：
前者把求值乘以调用次数，后者给执法多一个输入源、`失败朝安全` 就要多一条拒绝条件。
派工时投影，执法路径一个字不改 —— 它仍然只读策略集，只是这个集合多了一个来源。

它不撞 `重算的不能作判据`，因为判据的准确说法是：**能不能在不重做那次不可逆移动的前提下被重算出来**，
而不可逆的不是动作，是它在链上留下的、已被后一环引用的引用（`receipt 成链`）。
派工写进链的执行身份被引用着；拿计划重新生成一份策略，绑不到那个身份上。归档合并同理。

**它是派生物，不属于四族中的任何一族**：不是规则文件，是输出，没有人可以手写它。

**代价明说**：写入范围在派工那一刻冻结。计划改了而包已经在跑，要么重新派工（新身份、新 receipt），
要么这次不改。一个能在执行中途变宽的写入范围，等于没有写入范围。

#### 站也投影，机制相同

一站的执行者能动什么，来自方案的作用域声明：Stage 机上的「进」进入一站时，把该方案的作用域
投影成一份站级策略，在途到出站。派工投影的是包的写入路径，进站投影的是方案的作用域 ——
两次投影是同一个机制，同一条冻结规则。

#### 身份怎么到达执法

投影策略绑定执行身份，而执法在每次工具调用时只拿到宿主载荷。载荷里稳定存在的只有工作目录，所以：

> **执行身份由工作目录承载。** 派工与进站都记下这次执行的工作目录；执法用载荷里的工作目录找到在途的投影策略。

- 一个工作目录里只有一个在途执行时直接命中 —— 串行派工在主检出里就能跑，不需要额外机制。
- 要并行跑多个包，每个包派到自己的工作树里，集成那一格把它合回来。并行的隔离本来就要靠这个。
- 同一个工作目录里有多个在途投影时身份不可辨，按 `失败朝安全` 取它们的**交集**；
  一个都没有时，只有分发的策略生效。

不依赖宿主报出子 Agent 标识：那不是每个宿主都有的字段，工作目录是。

### 3.5 本地化区

每个站 Skill 里有一块由标记划出、归项目所有的区域，装「这个项目希望这一站怎么做」。

- **人写。** 它是项目对某一站提出的额外要求，与章程、清单同性质；Agent 可以建议内容，不自行写入。
  它不是断言也不是证据，§3.1 那张表管不到它。
- **只能加要求，不能减**（`本地化区只能加`）。它进不了判定，只进写作材料：改不了这一站产出什么、
  哪些门要跑、谁可以签名，也放宽不了 Skill 正文里的任何一条边界。
- **升级做移植，不做三方合并**：取出区域、放进新版同一位置、其余整体替换。
  区域之外的编辑在升级时被覆盖，并且明说被覆盖了 —— 一个留不住的编辑不会变成长期分叉。

## 4. 两条基线

治理的对象是两条**各自独立**的基线：

| | **规格** | **接口** |
| --- | --- | --- |
| 说的是什么 | **产品对外做什么** —— 让所有人对产品达成严格一致的理解 | **接口承诺什么** —— 模块之间怎么互相依赖，以及对外提供的 SDK / 服务接口 |
| 面向 | 对外（理解产品的人） | 对内（模块之间）**与**对外（SDK / 服务的调用方） |
| 条目 | Requirement，有 id | 元素，`<kind>:<selector>` 形式，可带摘要 |

**机制对称**：都是基线、都只由归档合并推进、都由一份 Change 级的 delta 提案、都需要一份索引、
都有独立的治理开关、Agent 都不许直接改基线。

**主题独立**：一条 Requirement **不映射到**任何一个接口元素，反过来也不。一次改动可以只动其中
一条。两者的关系是**语义上的**，不是**结构上的** —— 任何试图把它们对齐成一张表的机制，
都会在第一个「内部重构」上崩掉。（`机制对称主题独立`）

**推论**：任何只为其中一条设计的机制，都要先问另一条要不要 —— 但答案完全可以是「不要」。
对称的是机制的**形状**，不是机制的**内容**。

### 4.1 四种治理组合

| 规格 | 接口 | 这个项目在治理什么 | Change 欠什么 delta | 保证层 |
| --- | --- | --- | --- | --- |
| 开 | 开 | 产品行为 + 接口承诺 | 两份 | 开 |
| 开 | 关 | 只治理产品行为 | 规格 delta | 开 |
| 关 | 开 | 只治理接口承诺 | 接口 delta | 开 |
| 关 | 关 | 都不治理 | 无 | **关** |

第三种不是边角情况：一个 SDK 仓、一个基础库、一个基础设施仓，它的产品行为在别处被定义，
但它对外承诺的接口必须被治理。第四种也不是：一个项目可以只要流程与门，不要基线。

### 4.2 保证层是派生的

保证层是把基线与现实核对的那组东西：基线门与 `verify` 站的保证说明。
它的开关等于「治理了任意一条基线」。不给它独立开关，是因为那会放出两个不连贯的状态：

- **留着基线却什么都不证明** —— 危险的那个。一份「产品承诺 X」的记录，如果没有任何东西拿它
  跟现实核对，它不会保持诚实，而且**不会有任何人说它已经不诚实了**。
- **为不存在的基线做证明** —— 无意义的那个。

保留记录和证明记录，是一个决定，不是两个。（`保证层派生`）

## 5. 一个 Change 的骨架

一个 Change 走完它，靠的只有一样东西：

> **一个 Stage 的产出是它写下的文件。除此之外的一切都是草稿。**

会话上下文、命令回复、执行者脑子里的东西，都不在传递通道上。这条约束是三层共有的 ——
它决定了控制面为什么每次从磁盘重新解析（`一次调用一个进程`），
也决定了 Skill 那一层凭什么可以把一站放进隔离的上下文里跑。

### 5.1 站

站由流程定义，不是固定的。发行的三条流程是同一个序列的三种长度：

```
quick :  propose ─────────────────────────────→ apply → verify
solid :  propose ──────→ design → check ──────→ apply → verify
major :  propose → clarify → design → check ──→ apply → verify
```

后面还有一个**合成站 `ready-to-archive`** —— 它不在流程声明的站列表里，是最后一站走完之后
状态机所处的位置，终局审批在这里收。归档从这里发生。

这一族的任何文档在举例时都用这个列表。

### 5.2 两台状态机

```
Stage：      propose → … → verify → ready-to-archive → archive
工作包：      ready → running → integrated / failed / blocked
```

**归档不是第三台** —— 它是第一台最后那一格（`ready-to-archive → archive`），
只不过它是 Change 级的、只发生一次（`归档唯一例外`）。

> **一格的移动写一条 receipt，receipt 之间成链，链上的每一环被后一环引用。**（`receipt 成链`）

**写下一份文件不移动任何一格。** 一份交付记录写下来，工作包还停在 `running`，
由「进」拿它作入参移到 `succeeded / failed / blocked`；一次审批登记下来，Stage 还停在原地。
**台账与署名的断言都是移动的入参，不是移动本身** —— 这是 `写权限二分` 在状态机上的样子：
Agent 和人能写下依据，能不能走由控制面判。历史只增不改：删一环不是修复，是把它上面记录的一切一起废掉。

#### 人的确认之后，谁移动那一格

两台机器上都有「人签一个字，然后某一格该动了」的情形，答案不一样：

| | 人做什么 | 之后 |
| --- | --- | --- |
| **Stage 机**：审批 → 转换 | 批准这一站可以走 | **还有事做** —— 批完通常还要写东西、还要跑本站的门 |
| **工作包机**：确认 → 集成 / 评审 | 确认这一份交付我看过并认可 | **没有别的事** —— 确认就是这一格全部的入口条件 |

> **在工作包那台上，「证」默认捎带那一格的移动；在 Stage 那台上不捎带。**

理由和「进默认捎带产」相同：两件事总是连着做时，分开的唯一后果是有人忘了做第二件，
状态机停在一个条件全满足、却没人推的位置上。审批之后并不总是连着转换，那里分开是对的。

**捎带的是调用，不是记录，不是判定，也不是责任**（`捎带合调用不合记录`）：
「证」写审计事件，被捎带的「进」写 receipt，分开落盘；集成那一格该跑的检查（交付记录的形状、
改动路径是否落在包声明的范围内）照跑，跑不过就不动；诊断指向真正失败的那件事 ——
署名不成立与检查没过的补救完全不同（`出错给出路`）。

**代价明说**：「证」在两台机器上行为不一致，这一条必须在命令面上显式声明，不能让读者从动词名字去猜。

### 5.3 人的介入点

只有这五件事**没有任何机械手段能判定它**。它们共同的性质是：这一次登记就是它唯一的记录。

| 介入点 | 为什么没有门能判 | 频次 |
| --- | --- | --- |
| **审批一次转换或归档** | 没有门能判定「一个人是否同意」 | 站级按方案，终局按 Change；审批绑当时的内容修订，批完再改就作废 |
| **回答一条已存在的发现** | 门判的是「发现有没有被关闭」，不是「答得对不对」 | 一条一次 |
| **签署验证收据** | 门判的是各道门自己，没有门判「这一站确实验证过了」 | 一站一次 |
| **声明这个项目用什么命令验证自己** | 这正是门在问的那个问题 —— 门不能自己回答它 | 装配时一次 |

**四处，不是三处。** 最后一类经常被漏掉，因为它看起来像 Agent 的活；它不是 ——
签的是人，而签名正是它存在的全部理由。

**「确认一份交付」曾是第五处，2026-09-17 取消。** 集成有门能判（验证门当前且过、改动路径与工作树一致），
「我看过并认可」这一判断归到审批点：check 审批人对计划负责，终局审批人对全部交付负责。理由是生成量已经大到
逐包人工确认不现实；终局形态是审批由 MCP 服务的 AI 评审后给出，与人批同形。审批点按流程：quick 只有终局，
solid 加 check 出站，major 再加 clarify 出站（clarify 在规格侧，按 Change 计）。

**这张表同时是「一站需不需要人到场」的判据**：

> **人的介入点是这一站的主体，还是它的收尾？**

`propose` 与 `clarify` 的主体就是和人来回；`verify` 只在末尾要一个签名；`apply` 不需要人到场。
**主体需要人的站不能被隔离；收尾需要人的站可以隔离，但它必然以「需要人」出站一次。**

### 5.4 欠不欠的两个条件轴

流程声明每一站产出什么。一份产出是不是被欠着，取决于两件与「哪一站」无关的事：

| 轴 | 问的是 | 不满足时的状态 |
| --- | --- | --- |
| **治理依赖** | 这份产出依赖的那条基线，这个项目治理吗 | **不欠** |
| **侧** | 这份产出属规格侧还是实现侧；当前是不是主方案 | **不欠** |

两个轴是同一个机制的两个参数。要说死的是它的语义：

> **「不欠」与「待写」必须是两个不同的状态。** 「不欠」是一个答案，「待写」是一个任务。

把不欠说成待写，项目会去写一份没人会读的文件；把待写说成不欠，站会在缺东西的情况下放行。

## 6. 实现方案

一个 Change 可以有多个**实现方案**。典型是双路开发：一个方案写实现，另一个**从同一份规格出发、
不看实现**，独立设计出一套黑盒测试工程。

### 6.1 规格侧共享，实现侧分目录

| 侧 | 内容 | 带不带方案 id |
| --- | --- | --- |
| **规格侧** | 流程与分类声明、提案、规格 delta、接口 delta | **不带** —— 全 Change 一份 |
| **实现侧** | 作用域、设计、台账、证据、工作包、阶段状态、审批 | **带** |

**作用域在实现侧**，虽然它看起来像声明的一部分。它讲的是实现路径，而两个方案写的是不同的树 ——
留在共享的那一份里，一个方案的全部产出在另一个方案看来都是无人认领的。

**为什么规格侧必须共享**：双路开发的全部价值就在于两个方案面对的是**同一份判据**。
规格侧一旦也分方案，两边就各有各的标准，「独立验证」立刻退化成「各干各的」。
共享不是节省，是这个结构成立的前提。（`规格侧共享`）

**流程选择也在规格侧，所以所有方案走同一条流程。** 一个产出测试工程的方案，
它的 `design` 站设计的就是测试工程，站、门、出口条件不因此不同。

### 6.2 寻址到 (Change, 实现方案)

每个实现方案各有一套完整的状态机 —— 独立的 Stage 位置、独立的门运行记录、独立的审批、
独立的工作包计划。所以 §5.2 的「两台状态机」准确说法是**每个方案各有两台**。（`寻址到方案`）

**不给方案 id 就是默认方案**，默认方案不占用一个名字。这让单方案项目的每一次调用、
每一处目录布局都与没有这个特性时完全一样 —— **支持多方案不向任何单方案项目收费**。

**具名方案已实现（2026-09-17）。** 不给 id 就是默认方案，目录布局与单方案时完全一样；给了 id，实现侧落在 `changes/<id>/<scheme>/`。
每个方案各在自己的 worktree 里推进（会话设 `XFORGE_ROOT` 指回主检出、`XFORGE_SCHEME` 选方案），控制面拒绝两个方案共用一个工作目录。

### 6.3 归档是唯一的例外

归档是 Change 级的，只发生一次，两条基线的合并也只发生一次。由此：（`归档唯一例外`）

> **站级审批按方案收，终局审批按 Change 收。**

站级审批批的是「这个方案的计划可以进实现」—— 两个方案是两个不同的判断；
终局审批批的是「这次改动可以固化进基线」—— 那是一个判断，也只能有一个。

**归档要求这个 Change 已创建的每一个方案都到达 `ready-to-archive`。** 不再要的方案显式废弃，
不是被跳过 —— 批终局的人必须知道自己在为哪些方案的产出背书。

### 6.4 方案之间互不可见

这既是省 token 的规则，也是隔离的规则。在双路开发里它不只是省，
**它是「独立」这个词的全部含义**。要看另一个方案的东西，必须点名要（§8.3 第 2 级）。

## 7. 台账

### 7.1 台账只有一个形状

五类台账不是五种文件，是同一个结构的五套词汇：（`台账一个形状`）

```text
种类: <这是哪一种台账>
结论: <整体断言，可选 —— 「这次评审覆盖了哪几个维度」这类落这里>
条目:
  - 标识: <id，或它所针对的那个东西>
    结论: <这一条的判定>
    引用: [<可定位的东西：条目 id、路径、门名、摘要>]
    署名: <谁做了这个判定>       ← 只有需要人负责的结论才有，且与审计事件核对（§3.3）
    时间: <与署名成对出现>
    说明: <自由文本，控制面不读>
    承接: <返工 receipt id>      ← 返工之后重新决定时才有
```

### 7.2 五类台账

| 台账 | 标识 | 结论 | 引用 | 署名 |
| --- | --- | --- | --- | --- |
| 评审发现 | 发现 id | 未决 / 已决 | 涉及的产出、Requirement | 决定者 |
| 章程答复 | **章程标题（它就是 id）** | 符合 / 违反 / 不适用 | Requirement id、路径、门名 | 批准者（仅「违反」） |
| **出口条件**（一族） | 条目 id | 决定内容 | 承接的返工 receipt | 决定者 |
| 验证收据 | 门名 | 通过 | 门证据摘要 | 签署者 |
| 交付记录 | 执行 id | 成功 / 失败 / 受阻 | 改动路径、验证命令 | 执行者 |

**「出口条件」是一族，不是一份。** 每一个需要台账支撑的出口条件各有一份，落在同一个命名空间下；
这一版只有一个实例：材料问题。它是这一族的实例，不是第六类台账。

### 7.3 交付记录是混合体

它一半是机器已知的事实（执行 id、基线提交、改动路径、内容修订），由起草填；
另一半是断言（结论、遗留问题、完成判据的证据），必须由执行者填。
起草只填前一半 —— 这正是「工具不得代填断言」在文件层的样子。

### 7.4 受理

一份台账写下来之后，什么时候算被接受了？答案不是「再调一次命令」：

> **有门在验的台账，由门受理。** 门跑的时候读它、判它、把判定写进自己的运行记录。
> **没有门能判的断言，必须自己登记**（§5.3 的五处）。
>
> 判据是同一句话：**这个断言有没有一个机械手段能判它。有，归门；没有，归签名。**（`有门能判的不走证`）

这是「一个 Stage 只要很少几次调用」能成立的全部原因：若每份台账都要一次登记，
一个欠两份台账的站立刻翻倍。

**门是机制，但它被项目内容参数化。** 章程门要按这个项目自己写的章程标题逐条对照 ——
所以「门不知道项目在做什么」这句话要说准：**门的逻辑随脚手架分发，门的输入来自项目。**
混淆这两者，会推着人把项目内容写进门，或者把门的逻辑写进项目。

## 8. 上下文成本

> **上下文成本是一等约束，不是优化项。一份没人读的回复是一个缺陷。**（`上下文成本一等约束`）

控制面的读者是一个按 token 计费、并且会把每一次回复都带进后续每一轮的 Agent。
一次冗长的成功回复不是一次性开销，**它是这一站剩下所有轮次的固定成本**。

### 8.1 文件是权威，回复是视图

这两件事必须分开想，因为只有第二件是成本：

- **文件该多完整** —— 由「它要不要成为唯一权威」决定。
- **一次调用该发多少** —— 由「读者此刻要决定什么」决定（§2）。

把「文件大」当成「回复大」的原因，会推着人去拆文件；而拆完之后回复并不会变小，
漂移风险倒是真的多了一个。**正确的做法是文件保持完整，回复按需裁剪。**

### 8.2 能让控制面操作的就别开文件

直接读文件有三个问题：给的是全部（读者无法只要一部分）、不可审计（没有任何记录说它读过）、
而且它绕开了所有裁剪规则。控制面读同一个文件，可以只给这一刻需要的那一段，还能顺带说清
「这一段就是全部，你不需要再开文件了」。

### 8.3 加载三级

> **下一级绝不能被上一级顺手夹带。夹带是所有上下文浪费的来源。**
>
> （这里叫**夹带**，不叫捎带。`捎带合调用不合记录` 那条说的是动词之间刻意的合并，是好的；
> 这里说的是把下一级的内容混进上一级，是坏的。两件事不能共用一个词。）

| 级 | 内容 | 什么时候发 |
| --- | --- | --- |
| **0a · 不变量** | 治理开关、模块、路径；流程的判定图（站、门、出口条件、审批策略）；两条基线索引的**域层**；章程的标题清单；这个 Change 的声明 | 常驻 |
| **0b · 当下状态** | **当前实现方案**的位置与阻塞清单 | 常驻 |
| **1 · 按站** | 本站产出（写到哪、要哪些章节、指令）、本站台账的骨架、本站要跑的门、本站要读的上游文档（路径、大小、章节标题、自上次以来动没动 —— **不含正文**）、本站触碰的那个域下面的条目 id、**本站的 Skill** | 进入这一站时 |
| **2 · 点名** | 任何文档的正文、门的完整输出、历史 receipt 链、基线条目的正文、章程正文、**其它实现方案的任何东西** | 明确要才给 |

**「常驻」指在执行者的上下文里出现一次并保持有效** —— 随简报或第一次「读」进入；之后的「读」
默认只回 0b（`窄是默认`、`一事一次`），要 0a 得显式请求。

**第 0 级里不允许出现任何无界增长的东西**（`第0级有界`）。这就是基线索引必须分层的理由：
一个积累了几百条 Requirement 的项目，全量条目不小，而「常驻」是硬要求 —— 两条要求会互斥。

**0a 段必须是确定性的**（`不变量段确定性`）：时间戳、不稳定的排序、任何随运行变化的字段，
进去一个整段就破了。这条容易被无意破坏 —— 加一个「生成于」字段就够 —— 所以它是契约，不是建议。

### 8.4 定向与材料

**定向 = 0 级 + 1 级；材料 = 2 级。** 这两个词在这一族里只有这一个意思。

**发送顺序不等于分级**。分级回答「该不该发」，顺序回答「怎么排最省」。提示缓存按前缀精确匹配，
所以一次定向按稳定度排：`0a（跨站稳定） → 1（按站不同） → 0b（每次都变）`，0b 排在 1 之后。
它只在一个会话的开头有意义（简报、第一次「读」）；会话中途的回复前面已经分叉，排序无所谓。

**收益要诚实估计。** 0 级按设计就是小的，缓存省的是一个小东西的九成，而且缓存有存活时间。
成本是零，所以照做，但别拿它当别的东西的理由：**缓存解决价钱，不解决注意力** ——
命中的 token 仍然占着模型的注意力。

### 8.5 裁剪八条

每条都有名字，因为它们是这一族里唯一一批**会被三层同时引用**的规则。

**`正常就说正常`** 成功的回复应当短到可以不读。一次干净的转换不需要解释它做了什么 ——
它做成了，这本身就是全部信息。

**`出错给出路`** —— 给原因和下一步，不给讲义。 说清三件事：哪里错了、为什么这算错、下一步跑什么。
最后一项应当是可执行的命令本身。不要附带背景说明、设计理由或者一整套可选项 ——
读者此刻只要一条出路。

这条要多担一件事，因为**一次调用可以触发多个动词**（`捎带合调用不合记录`）：
「哪里错了」说的是**真正失败的那件事**，不是被调用的那个动词的名字。
一次「证」失败可能是署名不成立，也可能是集成检查没过，两者的出路完全不同。

**`大块给指针`** —— 给路径和摘要，不给正文。 通过的门给结论、身份和文件位置；失败的门才给正文 ——
因为读输出正是读者面对失败要做的事，这时候让他再发一次请求，恰恰是在他最付不起的时候收费。

**`名字不单飞`** —— 一个名字绝不单独出现。 给一个 id，就同时给读者接下来需要的东西。
**一个没有解释的名字是一个问题，而唯一能回答它的地方往往是最贵的那个文件。**

**`切片自称完整`** 明说「这是全部，不必再开文件」。一个不自称完整的切片，
会换来一次为保险起见的整份读取 —— 于是两份都在上下文里，比一开始就发全文更贵。

**`省略自报`** 省了什么、怎么取回来。一个安静丢掉一段的摘要，
恰恰在它最不配被信任的地方显得最可信。

**`一事一次`** —— 同一个事实一次回复里只出现一次。

**`窄是默认`** —— 宽要显式请求。 需要一个值的调用者应当能只取那一个值，
而不是收下整份回复自己切。

> `名字不单飞` 与 `切片自称完整` 不是礼貌规则。**Skill 那一层把它们当作机制前提**：它们成立，
> Skill 里那条对应的禁令（「不要打开那个文件」）才没有必要写；它们不成立，那条禁令写了也会输。
> 实测里它们不成立的样子：一站收到三个没有描述的产出名，去打开了两万字符的流程文件；
> 一次发了全文的调用之后，同一份文档又被重开了二十多次。**发了不等于不会再读。**

## 9. 跨层的非目标与已知限制

写下来是为了不被反复翻案，也为了不被误当成遗漏。

### 9.1 声明不设受理事件

一个 Change 的流程与分类声明，由 Agent 写下、控制面读取，就这样 ——
**没有署名、没有审计条目、不绑定内容修订。**

给它加一次登记是可行的，不加的理由有两条：一是**它会给每一个 Change 的开头加一次人工介入**，
而开一个 Change 本该是最轻的动作；二是**分类本来就要在后续的门下被反复检验** ——
一个声明自己没动接口的 Change，拦住它的是接口兼容性门。在写下那一刻先担保一次，
既挡不住说谎，又要为每一次诚实付费。

**代价要写全，包括第二条理由的限度**：那道门是**选配的**。在「规格关 / 接口关」的项目里
没有任何一道基线门在下游，于是「后续会被反复检验」这条论据归零，声明就是一份完全无人核对的自述。
**这是已知限制，不是遗漏。**

### 9.2 影响面自述

声明里的影响面是一个**列表**，「没有影响」是一个空列表 —— 那是一个断言，不是若干个 false
（加一个新的影响维度时，历史声明不会因为缺了一个布尔而同时失效）。

它的限度必须写在它旁边：**没有任何东西核对它。** 而 §8.3 第 1 级要给「本站触碰的那个域下面的
条目 id」，那个「哪个域」正是从这份自述推出来的 —— **写偏一个域，`先复用已有的名字再发明新的`
这条指令会静默失效**，而那恰恰是索引要解决的问题。链条的根是一个无人核对的输入，这一点要明说。

### 9.3 规格与接口不做结构对齐

不提供「这条 Requirement 由哪些接口元素实现」这类映射表。两者的关系是语义上的，
维护一张结构映射表的成本会落在每一次内部重构上。

## 10. 不变量

无论命令面、文件布局、Skill 写法怎么演进都不会变的东西。它们不是约定，
是这套系统能作为证据来源的前提。**子文档引用名字，不复述内容。**

| 名字 | 断言 |
| --- | --- |
| `写权限二分` | 工具能证明的，人不许说；人才能断言的，工具不许写。两个方向都是硬边界。 |
| `署名可引用不可编造` | 凡是记录判断的地方，名字都要对照仓库真实记录的身份校验；审计链是权威，门核对台账与它一致。 |
| `有门能判的不走证` | 单独登记只留给那些没有任何机械手段能判定的断言。 |
| `一次调用一个进程` | 每次从磁盘重新解析，不维护会话状态，两次调用之间什么都不记得 —— 记忆全在磁盘上，而磁盘上的东西是可审计的。 |
| `写必须能回退` | 落盘和记审计要么都成、要么都不成。一份没有审计背书的证据会解锁状态机，比没有更糟。 |
| `失败朝安全` | 读不出策略就拒绝，缺字段的退役声明视为仍然生效，不确定的身份视为未证实 —— 默认值都选更难通过的方向。 |
| `拒绝要留出路` | 任何一种全面拒绝状态，都必须允许诊断和修复它自己所需的那些操作 —— 而且只允许那些。 |
| `receipt 成链` | 两台状态机的每一格移动都写 receipt，链上每一环被后一环引用，历史只增不改。台账是移动的入参，不是移动本身。 |
| `捎带合调用不合记录` | 一个动词可以默认捎带另一个，条件是两件事总是连着做。捎带的是调用 —— 记录分开落盘、判定一个不跳过、诊断指向真正失败的那件事。 |
| `写入范围只有策略执法` | 能写哪些路径，只有权限策略拦得住。方案作用域在进站时、工作包计划在派工时被投影成策略，由工作目录承载身份；Skill 里的「边界」是提示 —— 一段散文永远不能扩大或缩小可写范围。 |
| `本地化区只能加` | 站 Skill 里归项目的那块区域只能加要求，不能减；它进不了判定。升级做移植，区域之外的编辑留不住，而且会被告知。 |
| `寻址到方案` | 一切判定寻址到 (Change, 实现方案)；不给 id 就是默认方案，默认方案不占名字。 |
| `归档唯一例外` | 归档是 Change 级的，只发生一次。站级审批按方案收，终局审批按 Change 收。 |
| `规格侧共享` | 规格侧全 Change 一份，实现侧按方案分。多个方案必须面对同一份判据，否则「独立」失去意义。 |
| `基线只由归档推进` | 两条基线没有第二个写者。一个第二写者会毁掉基线唯一拥有的那个性质。 |
| `机制对称主题独立` | 规格与接口形状可以互相借用，内容不许互相对齐；四种治理组合都合法。 |
| `保证层派生` | 治理了基线就要证明它，不治理就没什么可证明 —— 一个决定，不是两个。 |
| `台账一个形状` | 五类台账是同一个结构的五套词汇。出口条件是一族，不是一份。 |
| `不欠不是待写` | 治理开关关掉或不属于本方案的产出，状态是「不欠」，不是「待写」。 |
| `不读散文的意思` | 需要判定的事实必须先成为条目。不能指望从散文里提取它。 |
| `散文要有不可约判断` | 一份散文必须持有一个台账装不下的判断。没有，它就不该存在。 |
| `重算的不能作判据` | 能被重算出来的东西不能作为判定依据，除非它在不重做那次不可逆移动的前提下算不出来 —— 而不可逆的是它在链上留下的、已经被后一环引用的那个引用。 |
| `第0级有界` | 第 0 级不容纳任何无界增长的东西。 |
| `不变量段确定性` | 0a 段无时间戳、排序稳定；混进一个随运行变化的字段，整段前缀就破了。 |
| `上下文成本一等约束` | 不是优化项。一份没人读的回复是一个缺陷。 |
| `归档后不再变` | 归档后的记录冻结。它服务的是「后来的人」，而那个读者在若干年后才到。 |

## 术语

一行一个，只给定义；机制在正文。

| 术语 | 是什么 |
| --- | --- |
| **控制面** | XForge 命令行本身。只做四件事（§1），不写代码、不做判断 |
| **Change** | 一次改动的全部记录，一个目录，归档后冻结 |
| **流程** | 一个 Change 走哪些站、每站产出什么、凭什么离开 |
| **站（Stage）** | 流程里的一格；一站的产出是它写下的文件 |
| **门** | 控制面跑的确定性检查，输入来自项目，输出是绑定内容修订的运行记录 |
| **内容修订** | 一组产出文件的内容摘要；证据绑定它，不绑定提交 |
| **receipt** | 状态机每移动一格写下的一条记录；成链、只增不改 |
| **审计链** | 控制面写的、校验身份的事件链；署名的权威。审计索引是它的索引 |
| **执行身份** | 派工那一刻铸出、写进 receipt 的身份；投影策略绑定它 |
| **工作包** | Apply 站里一份可独立派工的工作：自有写入路径与验证命令 |
| **实现方案** | 一个 Change 的一条实现路径，各有一套状态机；不给 id 就是默认方案，给了就落在 `changes/<id>/<scheme>/` |
| **基线 / delta** | 同一份内容的两个生命阶段：在 Change 里叫 delta，归档合并后叫基线 |
| **台账** | Agent 或人写的断言文件，五类一个形状（§7） |
| **章程** | 项目的长期工程原则；标题是 id，正文是散文 |
| **清单** | 项目启用了什么、治理哪几条基线、跑哪条默认流程、用什么命令验证自己 |
| **本地化区** | 站 Skill 里归项目的那一块（§3.5） |
| **定向 / 材料** | 加载三级的 0+1 级 / 第 2 级（§8.4） |
| **保证层** | 把基线与现实核对的那组门与保证说明（§4.2） |
