# 测试架构：每一层回答什么问题

`README.md` 说各套件的职责，`RUNBOOK.md` 回答「我改了 X 该跑什么」。
**本文只回答一个问题：我要写一个新测试，它该放哪一层，凭什么。**

写它的直接原因是：这套测试已经有五层，但只有两层在目录结构里看得见，
另外三层散落在 `integration/` 里靠文件名辨认。一个不知道分层的人写测试时，
唯一能模仿的就是他最近读过的那个文件——于是格式契约被写成集成测试，
集成测试被写成黄金文件，而真正只有实跑能回答的问题被写成了静态断言。

---

## 1. 五层，按「回答什么」排列

| 层 | 位置 | 回答的问题 | 代价 |
| --- | --- | --- | --- |
| **单元** | `xforge/test/unit/` | 这个纯函数对吗？ | 毫秒 |
| **集成** | `xforge/test/integration/` | 这条命令在真实项目树上做对了吗？ | 秒 |
| **契约** | `xforge/test/integration/*-contract\|catalogue\|golden*` | 产品对外的**面**变了吗？ | 秒 |
| **产品** | `tests/` | 装出来、分发出去之后还成立吗？ | 分钟 |
| **实跑** | `tests/live-engine/` | 真实模型读得懂这份指令吗？ | **钱** |

前四层全部离线、确定、可以每次提交都跑。第五层不是。
**这条界线是整套设计的重点**：每往上一层挪一个问题，就少烧一次钱。

---

## 2. 决策树：我的测试放哪层

```
这个断言需要一个真实模型读一段散文并做出反应吗？
├─ 是 → 实跑层。没有别的办法，见 §6。
└─ 否 ↓

它断言的是「产品对外承诺的某个集合」吗？
   （诊断码表、导出符号、命令与 flag、受治理文件格式、Skill 指令的路径与命令）
├─ 是 → 契约层。用 golden 记录，让变化成为可 review 的 diff，而不是某人事后的发现。
└─ 否 ↓

它需要 CLI 进程、真实项目树、真实 git 吗？
├─ 是 → 集成层。
└─ 否 → 单元层。
```

**最常被放错的一格是契约层。** 判据很简单：
如果这个断言的失败信息应该是「这个集合变了，请确认是有意的」而不是「这里错了」，它就是契约。

---

## 3. 契约层：现有的九份

契约层没有自己的目录（原因见 §5），靠这张表辨认：

| 契约 | golden | 它保护什么 |
| --- | --- | --- |
| 诊断目录 | `diagnostics/catalogue.txt` | 产品能说的每句话的**码与严重度** |
| 未被测试的诊断码 | `diagnostics/untested-codes.txt` | 债务清单，**只能缩短** |
| 已发布 API | `public-api.txt` | `src/index.ts` 导出的符号 |
| CLI 认领的命名空间 | `contracts/cli-claimed-namespaces.txt` | 哪些路径形状会被解析成特定的东西 |
| Skill 指令的证据路径 | `contracts/skill-evidence-paths.txt` | Skill 教 Agent 往哪写 |
| **Skill 指令的命令** | `contracts/skill-commands.txt` | Skill 教 Agent 跑什么 |
| **CLI 有而无人教的能力** | `contracts/skill-unmentioned-commands.txt` | 产品长出来、说明书没跟上的部分 |
| **受治理文件格式** | `contracts/governed-formats.txt` | 每个格式由什么强制执行 |
| **无 schema 的台账** | `contracts/unschemad-ledgers.txt` | Agent 手写、靠读取方自行判断的文件 |

加粗的四份是这一轮新增的。前两份回答「Skill 和产品是否还对得上」——
这个问题过去只有实跑能回答，现在离线就能答一部分。

### golden 的三种用法，别混

1. **指纹**：整个集合，任何变动都要人确认。诊断目录、导出面。
2. **债务清单，只能缩短**：`untested-codes.txt`。**新增条目必须被质疑**。
3. **可 review 的产物**：`projection/`、`envelope/`。它记录的是产品真实产出的字节。

重录用同一次运行加一个环境变量：`XFORGE_UPDATE_GOLDEN=1 npx vitest run <file>`。
**故意不做成独立脚本**——单独重录一份 golden 正是「把回归记录成新的真相」的做法。

## 4. red-first：它证明什么，以及它的一个硬约束

`npm run check:red-first` 把这次改动**动过的每个测试文件**拿到父提交上跑，
要求它们在那里变红。通过了说明这个测试不区分好坏，判失败。

**硬约束（这一轮踩到的）**：一个「因为兼容性而被改动」的测试文件也是候选。
给 `KnownIdentities` 加了一个必填字段之后，三处手写的 fixture 必须补字段——
那个文件因此进入候选、在父提交上照样通过、被判 `NOT PROVED`，整个 verify 红。

两条应对，选一条：

- 给那个文件补一个**真正区分**新行为的断言（推荐，那个行为本来也该有测试）
- 让新字段可选，从而不必改 fixture（只有在字段确实可选时才诚实）

**推论一：纯粹的测试文件移动做不到。** 换目录而内容不变的文件在父提交上会通过，
必然 `NOT PROVED`。这就是为什么契约层没有自己的目录——
把它做出来的代价是同时修改七个文件的内容，那比没有目录更坏。

**推论二：red-first 保护不了契约测试，而且它的绿是虚的。**
它只把**测试文件**拷进基线 worktree（`red-first.mjs` 的注释写明了这是刻意的：
「其余一切——src、scaffold、schemas——保持基线原样，这正是全部意义所在」）。
于是一个新契约测试的 golden 在基线上**不存在**，`golden()` 返回占位符，断言失败，文件判红。
它通过了 red-first，但通过的理由是「golden 文件缺失」，不是「它区分了修好与没修好」。

所以：**新增契约测试时，red-first 的绿不构成任何证据**。
这类测试的价值要靠人在 review 时读那份首次录制的 golden 来确认——
见 §7 第 4 条。这不是缺陷，是 red-first 的适用范围：它为「修 bug 时附带的测试」设计，
而契约测试记录的是既有事实，本来就没有 bug 要证。

## 5. 目录结构为什么长这样

```
xforge/test/
  unit/            纯函数
  integration/     其余全部（集成 + 契约）
  fixtures/golden/ 所有 golden
  helpers.ts       fixture()、runCli()、推进 Stage 的助手
  project-builder.ts  project().flow('solid').packages(1).atStage('apply')
tests/
  *.test.ts        产品面黑盒
  live-engine/     实跑
```

`integration/` 里混着两层，是 §4 那条约束的结果，不是没想过。
辨认靠文件名：`*-contract.test.ts`、`*-catalogue.test.ts`、`*-golden.test.ts` 是契约层。
**新增契约测试请沿用这三个后缀之一**，这是目前唯一能把它和集成测试分开的信号。

---

## 6. 只有实跑能回答的问题

静态测试能证明 CLI、Gate、控制面按约定工作。它证明不了这些：

- 一份 Skill 的**散文**是否可被理解、是否会被遵守
- Artifact 的 `outline` 是否真的引导出符合结构的产物
- 一条诊断的措辞是否真的把读者引向正确的下一步
- 冷启动（`*-cold` 场景）下，没有 prompt 里的答案，产品自身是否够用

前三条是**措辞质量**，第四条是**产品毛边**。都只有让真实模型读一遍才知道。
这也是这里不保留录制/回放的原因：回放用录像顶替模型输出，恰好跳过唯一要验证的东西。

**新增的两份 Skill 契约 golden 缩小了这个集合，但没有消灭它。**
它们能证明「Skill 点名的命令和 flag 真实存在」「中英两版教的是同一批命令」，
证明不了「这句话说清楚了没有」。

---

## 7. 加一个新契约时的清单

1. 决定它是三种 golden 里的哪一种（§3），并在测试的文档注释里写明**为什么是这一种**
2. 文件名用 `*-contract.test.ts` / `*-catalogue.test.ts` / `*-golden.test.ts`
3. 从**源码或产品输出**推导，不要手写清单——手写的清单会陈旧，而陈旧的契约比没有更坏
4. 第一次 `XFORGE_UPDATE_GOLDEN=1` 之后**逐行读一遍**再提交
5. 如果它是债务清单，在测试里写清「只能缩短」，并说明什么情况下允许增长
